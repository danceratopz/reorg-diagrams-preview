Blockchain Engine Reorg Tests ¶

The Blockchain Engine Reorg Test fixture format tests are included in the fixtures subdirectory blockchain_tests_engine_reorg, and describe a DAG of Engine API payloads plus a branching script of Engine API / JSON-RPC steps to verify chain reorganization behavior.

These are produced by the ReorgTest test spec.

Description¶

Unlike BlockchainEngineFixture (a linear payload list where the consumer always sends forkchoiceUpdated(head=payload) after each payload), this format lets a test describe side chains, explicit forkchoice states (head, safe, finalized), multiple legal outcomes per step, outcome-specific follow-up steps (branches), client-built payloads (getPayload binds the built payload to a new label), and transaction-pool observations.

Every block in the DAG names its parent by label instead of relying on list order, so sibling blocks and blocks built on top of an invalid block are first-class. Every hash-valued step field is a label ("genesis" is reserved for the genesis block, "zero" for the zero hash, and "latest"/"null"/"any" are reserved RPC tags/special values valid only where a field's description says so; labels introduced by getPayload.bind are resolved at run time); the consumer resolves labels to hashes itself, so fixtures are byte-identical across clients.

Each step's expect field is a list of legal outcomes (the Engine API reference model fills it in at fill time for any step an author left unannotated, deriving the outcomes the execution-apis specification allows a conformant client to return); the consumer selects the first outcome matching the observed response and runs that outcome's branches steps.

Every outcome in a step's expect, model-filled or hand-authored, must be spec-permitted at that point, so a passing fixture establishes conformance. Where the specification is ambiguous, an outcome is marked disputed with a reference or rationale; a client's spec violation is never added as an alternative.

A single JSON fixture file is composed of a JSON object where each key-value pair is a different HiveFixture test object, with the key string representing the test name.

Consumption¶

For each HiveFixture test object in the JSON fixture file, perform the following steps:

  1. Start the client under test using:

    • network to configure the execution fork schedule according to the Fork type definition.
    • pre as the starting state allocation of the execution environment for the test.
    • genesisBlockHeader as the genesis block header.
    • HIVE_ENGINE_MAX_REORG_DEPTH, derived from minReorgDepth, if present. Only the geth and erigon hive wrappers read it, and only from ethereum/hive#1608 on.

  2. Send an initial engine_forkchoiceUpdatedVX to the genesis block and verify it returns VALID; verify the client's genesis block hash via eth_getBlockByNumber(0).

  3. Run steps in order. For each step:

    1. Resolve every label referenced by the step to a hash (or to the label itself, for a client-built payload not yet bound).
    2. Send the request (or perform the RPC observation).
    3. Select the first entry of the step's expect list whose constraints match the observed response; fail the test if none match.
    4. Run the steps listed in branches under the matched outcome's id, if any (recursively).

Structures¶

HiveFixture¶

- network: Fork¶

Fork configuration for the test. It is guaranteed that this field contains the same value as config.network.

- config: FixtureConfig¶

Chain configuration object to be applied to every client running the test.

- genesisBlockHeader: FixtureHeader¶

Genesis block header.

- pre: Alloc¶

Starting account allocation for the test. State root calculated from this allocation must match the one in the genesis block.

- blocks: Mapping[String,FixtureReorgBlock]¶

The block DAG, keyed by label.

- steps: List[Step]¶

Ordered, branching script of Engine API / JSON-RPC steps.

- minReorgDepth: Optional[Number]¶

Minimum side-chain reorg depth (in blocks) the client must apply without refusing for capacity reasons; the consumer sets the client's cap (HIVE_ENGINE_MAX_REORG_DEPTH) to it. None keeps client defaults.

FixtureReorgBlock¶

- parent: String¶

Label of the parent block ("genesis" for a block extending the genesis block).

- payload: FixtureNewPayloadRequest¶

The block's engine_newPayloadVX request: params (version-dependent parameter tuple, see FixtureEngineNewPayload) and newPayloadVersion.

- validationError: Optional[TransactionException|BlockException]¶

Present for an invalid block only: the exceptions a client may report for it, any one of them, in the form of FixtureEngineNewPayload.validationError. A payload that does not hash to its blockHash lists BlockException.INVALID_BLOCK_HASH; a test can also list that exception for a block whose hash is correct, so the field does not tell the two apart. The field is informative: a consumer judges a client by the expect of the steps, which can accept other answers for an invalid block (ACCEPTED or SYNCING on a side chain, for example). Fixtures with this field do not load in versions of the framework from before it was added.

Step¶

A step is one of the variants below, distinguished by its type field. Every variant shares:

- type: String¶

One of newPayload,forkchoiceUpdated,getPayload,assertHead,assertCanonical,assertState,assertReceipt,assertLogs,sendRawTransaction,assertTxStatus,servePeer,awaitHead.

- description: Optional[String]¶

Human-readable description of the step, for logging.

newPayload¶

  • block: String — label of the block (or a getPayload-bound label) to send via engine_newPayloadVX.
  • expect: List[Outcome] — legal outcomes.
  • branches: Mapping[String,List[Step]] — follow-up steps per matched outcome id.

forkchoiceUpdated¶

  • head / safe / finalized: String — labels; safe/finalized default to "zero".
  • version: Number — engine_forkchoiceUpdatedVX version; when unset, that of the payload attributes' fork for a build request, else of the head block's fork.
  • payloadAttributes: Optional[PayloadAttributes] — if set, a payload build is requested.
  • expect / branches: as above.

getPayload¶

  • bind: String — new label for the built payload.
  • version: Number — engine_getPayloadVX version; when unset, that of the retrieved build's fork.
  • parent: String — expected parent of the built payload.
  • transactionsInclude / transactionsExclude: List[TxRef] — transactions that must (or must not) be in the built payload.

getPayload retrieves the build whose payloadId the last forkchoiceUpdated that did not error returned. Filling rejects a getPayload with no such build, one on another parent, or one that depends on which outcome of an earlier step occurred. A bound label's forkchoiceUpdated and newPayload versions are those of its build's fork.

The wait before engine_getPayloadVX is the consumer's --get-payload-wait-time option, not a fixture field.

assertHead¶

  • latest / safe / finalized: Optional[String] — expected labels, checked via eth_getBlockByNumber.

assertCanonical¶

  • blocks: Mapping[HexNumber,Optional[String]] — expected label (or None for "no block") at each height.

assertState¶

  • at: String — block label or "genesis" (that block's own state; it must be canonical when the step runs), or "latest". Default "latest".
  • accounts: Mapping[Address,AccountExpectation].

assertReceipt¶

  • tx: TxRef.
  • block: Optional[String] — expected receipt block label, or None for no receipt.
  • status: Optional[HexNumber].

assertLogs¶

  • address: Optional[Address].
  • fromBlock / toBlock: HexNumber|String — defaults "earliest" / "latest".
  • blocks: List[String] — labels whose logs must appear, one entry per expected log.

sendRawTransaction¶

  • tx: TxRef.
  • expect: List[String] — subset of ["accepted", "rejected"]; default ["accepted"].

assertTxStatus¶

  • tx: TxRef.
  • expect: List[String] — non-empty subset of ["included", "pending", "dropped"], preferred first. The consumer polls eth_getTransactionByHash until the status is the first listed one; once its deadline passes, any listed status is accepted.
  • includedIn: Optional[String] — required block label when included matches.

servePeer¶

  • head: String — label of the block whose chain, from genesis, a devp2p peer serves to the client; the consumer dials the peer into the client on the first servePeer step. A later servePeer switches the served chain, and the peer still answers requests by hash for earlier ones. A client may download a block's missing ancestors from the peer within a newPayload or forkchoiceUpdated call, so a head is announced before servePeer.

awaitHead¶

  • latest: String — label of the block the client must sync from the peer and make its head, after a forkchoiceUpdated to it answered SYNCING. That update keeps safe and finalized, which a client may apply with the head or only on a later update. The consumer polls eth_getBlockByNumber("latest") for up to 60 seconds. It sends the newPayload of that block and that forkchoiceUpdated again after 0.5 seconds and then every 3 seconds, redialing the peer first if the client dropped it. An INVALID answer to either fails the step at once.

The Engine API never requires a client to sync: paris.md only says a client MAY start one. awaitHead is therefore a liveness expectation beyond the specification, and a failure means the client did not reach the head in time while the update was repeated, not that it violated the Engine API.

Between servePeer and awaitHead the client may make the synced block its head at any moment. The filler therefore accepts only servePeer, and a newPayload or forkchoiceUpdated with an authored expect, between the two.

Outcome¶

One legal outcome of an Engine API step. Every set field is a constraint; unset fields are not checked. Each outcome sets errorCode/anyError, status or headMoved: the other fields alone are also met by a SYNCING or INVALID response.

- id: String¶

Identifier, unique within the step's expect; selects the branches entry to run when matched.

- disputed: Optional[String]¶

If set, the specification is ambiguous about this outcome; the value is a reference (e.g. an issue URL). A disputed outcome still passes.

- status: Optional[String]¶

Expected payloadStatus.status (VALID,INVALID,SYNCING,ACCEPTED,INVALID_BLOCK_HASH).

- latestValidHash: Optional[String]¶

Expected latestValidHash as a block label, "null", or "any". A SYNCING outcome always expects "null".

- errorCode: Optional[Number]¶

Expected JSON-RPC error code (e.g. -38002,-38006).

- anyError: Optional[``Bool``]¶

If true, any JSON-RPC error matches (for uncoded errors).

- headMoved: Optional[``Bool``]¶

forkchoiceUpdated only: whether latest equals the requested head right after the call. Distinguishes an applied update from a no-op when both answer VALID with the same latestValidHash.

- validationError: Optional[String]¶

"required" or "none": whether validationError must be present or absent.

- payloadId: Optional[String]¶

"nonNull" or "null", for a forkchoiceUpdated with payload attributes.

PayloadAttributes¶

Payload attributes sent with forkchoiceUpdated to start a build; fields match the Engine API's PayloadAttributesVX.

AccountExpectation¶

- balance / nonce: Optional[HexNumber]¶

- storage: Optional[Mapping[Hash,Hash]]¶

- code: Optional[Bytes]¶

Expected eth_getCode result; 0x for an account without code.

TxRef¶

Reference to a transaction of a fixture block.

- block: String¶

- index: Number¶

Default 0.

Differences from Blockchain Engine Tests¶

  1. Block DAG, not a list: blocks name their parent by label, so side chains, invalid-block descendants and re-convergence are first-class.
  2. Branching step script: steps is not a flat payload list; a step's expect can list several spec-legal outcomes and branches continues down the outcome that was actually observed.
  3. Explicit forkchoice state: forkchoiceUpdated steps set head/safe/finalized independently instead of always following the last payload.
  4. Client-built payloads: getPayload retrieves and binds a payload the client built itself, which can then be delivered back via newPayload.
  5. State observations: assertState/assertReceipt/assertLogs/assertTxStatus steps check observable RPC state after a forkchoice update, instead of a single fixture-wide post allocation.

Fork Support¶

Blockchain Engine Reorg Tests are only supported for post-merge forks (Paris and later), as they rely entirely on the Engine API.
